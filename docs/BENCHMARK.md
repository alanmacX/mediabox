# 媒体性能测试说明

## 固定工作负载

跑分使用随 HAP 打包的 2048×1152 JPEG、1280×720/30fps/4s H.264 + AAC MP4、GIF，以及应用生成的 5s/48kHz 单声道 PCM WAV。测试前复制样例，不把复制、编码器探测或媒体信息读取算进各项耗时。样例源文件用 `scripts/generate_benchmark_fixtures.sh` 在开发机生成；发布版直接使用仓库中已生成的文件。运行时不再尝试生成不同编码格式的视频，因此硬件转码和 Remux 使用相同输入。

固定素材和多次测量遵循媒体性能测试需要控制输入的基本原则。FFmpeg 官方 [`-benchmark` 文档](https://ffmpeg.org/ffmpeg.html)将实际时间、用户时间、系统时间分开报告；本应用用系统单调时钟测量用户等待的实际时间，包含产品引擎启动、读写和编码，指标分别是 MP/s、MB/s 或媒体时长与耗时之比。

参考 [Google Benchmark 的预热、重复测量和变异系数](https://github.com/google/benchmark/blob/main/docs/user_guide.md)以及 [hyperfine 对短任务启动开销和缓存的处理](https://github.com/sharkdp/hyperfine/blob/master/README.md)：每项先通过产品 pipeline 预热一次，再测三个固定批次，取每次操作耗时的中位数；短任务通过批量执行把单批测量延长到约 1 秒。各项固定批量次数依次为：图片缩放 6、拼接 3、硬件视频转码 2、AAC/MP3 各 12、响度标准化 4、Remux 24、GIF 16。报告保留每批耗时、批量次数和变异系数。FFmpeg 引擎直接读取应用私有缓存中的素材，避免每次计时都额外复制源文件。每次执行仍要求引擎完成且输出文件至少 1 KiB。

视频素材必须能由 Media Kit 识别为 1280×720、约 4 秒；硬件转码要先通过系统能力检查。固定源有 AAC 音轨，避免 AVTranscoder 以有音频配置处理无音轨视频。

## 结果语义

8 项全通过才显示总指数；缺素材、不支持、执行失败或超时均显示“未完成”及具体原因。`media-v2` 采用固定参考吞吐量：单项指数为 `100 × 实测吞吐 / 参考吞吐`；总指数为 `500 × 各项吞吐比的等权几何平均`。**100 和 500 分别是参考值，不是满分；指数没有固定上限。**在所有子项都翻倍的条件下，总指数也翻倍。页面显示原始吞吐和相对参考值，不使用会封顶的进度条或“旗舰”等固定档位。这个指数只描述本项目固定工作负载的相对吞吐，不等同于其他跑分软件的分数。

| 工作负载 | `media-v2` 固定参考吞吐量 |
| --- | ---: |
| 大图缩放编码 | 47 MP/s |
| 双图拼接 | 23.5 MP/s |
| 视频硬件转码 | 1.8× 实时 |
| 音频转 AAC | 61.5× 实时 |
| 音频转 MP3 | 41× 实时 |
| 响度标准化 | 12.75× 实时 |
| 无损封装 Remux | 41 MB/s |
| GIF 优化 | 6.2× 实时 |

参考吞吐量沿用上一版总分内部使用的固定向量，故本轮仅去掉 1000 截顶时，低于截顶的总指数数值不变。参考向量是本项目内部基线，并非经跨设备标定的“标准机”。版本号、各项参考值和原始测量一起写入报告。改变素材、编码参数、计时边界、批量负载或参考向量时须升级版本；不同版本不能直接比较。固定参考基线与几何平均的做法可参看 [Geekbench 6 的基准分说明](https://www.geekbench.com/doc/geekbench6-benchmark-internals.pdf)和 [SPEC CPU2017 的参考机与比率说明](https://spec.org/cpu2017/Docs/overview.html)。FFmpeg H.264 硬件编码器的短任务探测在计分任务结束后进行，只进入设备诊断信息，不影响任何子项计时。

报告记录测试前后系统热状态以及各项波动率。热状态变化或变异系数偏高时，数值反映设备状态变化，不应解释成固定的硬件性能差异。

底层 `@prq/ffmpeg-tools` 的 FFmpegManager 只有一个执行线程，超时取消不保证正在执行的 native FFmpeg 命令立刻停止。因此首个 FFmpeg 计分任务若超时，剩余 FFmpeg 项会标记为受阻；这表示本轮测试无效，并非编码器缺失。编码器短任务探测已串行化，探测超时不缓存为“缺失”。

## 验证

在开发机运行 `node tests/benchmark-score.test.cjs` 和 `node tests/ffmpeg-capability.test.cjs`，再用 DevEco/hvigor 构建 HAP。设备复测可通过 `aa start -b com.mediabox.app -a EntryAbility --ps bench 1` 自动打开性能页；各项原始指标和失败原因会写入应用缓存目录的 `bench_report.txt`，并以 `BenchItem` 标签输出到 hilog。

参考的 [OpenHarmony 代码问题分析 skill](https://gitcode.com/openharmonyinsight/openharmony-skills)仅用于调用链和状态追踪方法；媒体 API 的参数以本项目所用 SDK 声明和设备返回值为准。

2026-09-18 旧版验证：连接的 HarmonyOS API 24 设备完成 8/8，约 4 秒，`h264_ohosavcodec` 短任务探测成功；连续三轮旧版总分 509、471、468，AAC 与 MP3 项波动远大于硬件视频项。新版延长测量并更换总分公式，旧分数不可与新版横向比较。API 24 模拟器未支持 AVTranscoder，按规则不发布总分。

同一真机安装首轮新版后连续两轮均为 8/8、约 17 秒，总分 610、627，相差约 2.8%；测试前后热状态均为 0。最大批次变异系数分别为 15.0%、22.8%，主要仍来自耗时很短的 GIF 项。随后增加固定批量次数；这会改变热负载和分数，应单独比较增加负载后的重复结果。报告原始批次耗时比单看总分更适合判断本轮可信度。

增加负载后的同一真机三轮均为 8/8，耗时 27、26、25 秒，总分 574、593、596；最大批次变异系数 9.3%、7.4%、9.4%，测试前后热状态均为 0。第一轮是安装后首次启动，其分数较低；后两轮在同一进程中相差约 0.5%。这组数据表明单轮采样噪声已降低，也表明冷启动与设备频率状态仍会影响跨轮结果；比较设备时宜保持相同的预热与运行条件。

`media-v2` 指数和报告格式在同一真机验证：8/8，约 25 秒，总指数 592，报告含版本、各项参考吞吐与实际吞吐，FFmpeg H.264 探测成功。去掉截顶后，本次结果因原值低于 1000 而保持相同数值；超过 1000 的计算路径由单测覆盖。
