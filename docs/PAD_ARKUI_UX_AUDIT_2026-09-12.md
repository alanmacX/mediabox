## 3. 现状信息架构与重复入口判断

```text
工具 Tab / 首页
├─ 自动识别 → 照片图库 / 文件
├─ 按类型打开 → 视频 / 图片 / GIF / 音频 / 字幕 / 动态照片
│  └─ 图库或文件（多选上限 50）
├─ 单个文件 → 工作台 → 工具配置 → 任务进度（二级 TasksPage）
│                         └─ 返回工作台
├─ 多个文件 → 批量处理 → 页面顶部配置 → 任务进度
└─ 任务 Tab → TasksPage（同一队列，另一种布局）
```

| 当前入口 | 结论 | 建议归属 |
| --- | --- | --- |
| 自动识别 + 按类型导入 | 来源相同但类型过滤不同，不能简单判定完全重复 | 保留通用导入为主入口，类型入口压缩为次级快捷入口 |
| 图库与文件 | 来源与支持格式不同，应保留 | 图库用于图片/视频，文件用于所有支持类型；说明可多选 |
| 任务 Tab + 二级“任务进度” | 同一完整队列被重复呈现，入口上下文还改变列数 | 一个任务中心；详情按 taskId / batchId 定位 |
| “提取音频” + “提取 MP3” | 前者已能选择 MP3，存在功能重叠 | 一个提取音频面板，MP3 为预选格式快捷方式或直接收敛 |
| 智能压缩 + 最高质量/平衡/更小/最快 | 同一参数流程被拆为多个长列表项目 | 一个压缩入口，面板内选择预设并显示实际输出差异 |
| 图像“格式转换” + 多个“转格式” | 当前“格式转换”其实固定 WebP | 一个格式转换入口 + 格式选择，必要时保留最近格式快捷项 |
| 媒体信息 + 预览参数摘要 | 信息层级不同，应保留 | 信息入口贴近文件摘要，不占“推荐处理”首屏名额 |
| 返回箭头 + 部分面板取消 | 可能有不同退出语义，但当前缺少草稿模型 | 统一导航返回；取消仅用于撤销当前配置，需明确说明 |

保留已有优点：File First、系统 Picker、多文件统一任务队列、无损/重编码区别、能力探测、保存与分享分开、预览说明编码质量以输出为准、原生导航返回和转场。不要为了去重删除不同编码语义的功能（例如无损封装与重编码、精确裁剪与关键帧裁剪）。

## 5. 逐项修改规格

### UX-01 · P1 · 运行中的任务“删除”会使真实处理失去可见记录

**证据 C/T**：`core/task/TaskQueue.ets:210 removeTask()` 对 RUNNING/CANCELING 调用 `cancel()` 后，无论返回值都过滤掉任务；`ui/components/TaskCard.ets:140` 附近对所有状态显示 28×28 删除按钮；`pages/TasksPage.ets:90 deleteTask()` 无条件提示“已删除该记录”。执行器仍持有 task 引用并可能继续工作。

**本轮隔离复现**：使用现有测试文件的生产代码加载器与模拟 SDK，让执行器处于 RUNNING 且 cancel=false，调用 removeTask 后可见记录为 0，执行完成后仍为 0。未触碰模拟器真实任务。记录见 [queue-remove-reproduction.json](ui-audit-2026-09-12/queue-remove-reproduction.json)。

**影响**：用户误以为处理已经停止，实际仍耗资源；完成输出失去队列入口。即使取消已接受，CANCELING 尚未完成也不应消失。

**修改**：RUNNING 只显示“停止”；CANCELING 显示“正在停止”并禁用重复请求。仅终态允许删除记录。队列层必须拒绝活动任务的直接删除，不能只靠 UI 隐藏。删除方法返回明确结果，页面据此反馈；等待任务先取消再按产品语义删除。

**验收**：模拟执行器 cancel=false，点击停止后记录仍在且持续更新；cancel=true 后先保留 CANCELING，收到完成回调后进入 CANCELED；清理终态不影响活动任务。扩展现有 `tests/task-queue.test.cjs` 覆盖这些分支。

### UX-02 · P1 · “保持宽高比”只约束了宽度输入

**实测 V**：包内1280×720图片，锁定比例后仅把高改为360，宽仍1280，见第2节截图。

**证据 C**：`AdjustmentPanel.ets:262 changeWidth()` 修改高度；`:383` 宽度走该函数，而高度回调仅 `heightText = v`。Toggle 打开也只改布尔值。

**修改**：使用唯一的尺寸编辑函数，传入被编辑维度；锁定时双向换算，视频按有效偶数像素规则处理。锁定重新打开时以最近编辑维度或清晰规定的宽度为基准恢复比例；宽、高、比例和预览保持一致。

**验收**：1920×1080 改高为 720 得到 1280×720；改宽为 960 得到 960×540；解除锁定允许自由尺寸；重新锁定不保留错误比例；视频奇数输入显示规范化值或明确错误。

### UX-03 · P1 · 快速输入可能让预览停在旧参数

**证据 C/R**：`AdjustmentPanel.ets:154 schedulePreview()` 350ms 防抖；`:272 updatePreview()` 忙碌时直接 return。若新防抖回调发生在旧预览完成前，本次请求丢弃，旧请求又可能因 settings 不一致丢弃结果；finally 未补跑最后请求。`previewStale` 存在但显示文字仍可能是“预览随参数自动更新”。这是源码确认的竞态窗口，实际触发频率待设备测量。批量水印用手动更新，改顺序/参数后仍展示旧图，仅有一般性说明。

**修改**：记录 desiredRevision / renderedRevision；渲染期间只合并到最新请求，finally 若版本落后继续渲染。离页停止更新并释放 PixelMap。参数变化立即显示“预览待更新”，最新预览成功才清除；失败保留错误与重试。批量水印同样绑定文件顺序和参数指纹。

**验收**：注入慢预览，连续修改 5 次，停止输入后最终画面对应第 5 次；旧请求不能覆盖新画面；退出无回写；预览失败不伪装成功。只对影响构图的字段更新构图预览，编码质量改变不必重复解码同一帧。

### UX-04 · P1 · 目标大小输入被静默修正

**证据 C**：`ToolConfigPage.ets:53` 使用 `Math.max(1, Number(text) || 25)`，空值/0 变 25MB，小于 1MB 变 1MB，缺少有限值校验。

**修改**：trim、有限正数和明确范围校验，不以默认值替代非法输入。若引擎允许小目标，应支持如 0.5MB；若业务有限制，在字段下明确范围并拒绝提交。显示原文件大小、目标大小、缩小比例，以及不能保证质量的解释。估算与实际值清楚区分。

**验收**：空值、0、负数、超大值、Infinity 文本不得创建任务；0.5MB 按能力接受或明示范围，绝不能暗中成为 1MB；字段仍显示用户输入，错误靠近字段。

### UX-05 · P1 · 批量输入角色和处理范围不透明

**证据 C**：`BatchWorkbench.ets:155 videoAndAudio()` 接受 1 视频 + 多音频；`:372 enqueueReplaceAudio()` 只取 `audios[0]`。`:253` 附近视频批量压缩遇不支持文件直接 continue，部分成功时不报告跳过明细。图片水印/复制元数据的角色由第 1/2 个文件隐式决定。

**修改**：替换音轨只接受 1+1 或让用户明确选择音轨；多余输入不得静默忽略。显示“主视频”“替换音频”“底图”“水印图”“元数据来源/目标”角色，并允许交换。批量预检输出可处理/不可处理名单、原因和实际创建数；部分成功后可重试失败项。

**验收**：1 视频+2 音频必须明确选用哪一个；无效文件不无声消失；5 文件中 2 不兼容时显示“将处理 3 个，2 个需调整”；更换输入顺序后角色标签、预览和最终参数一致。

### UX-06 · P1 · 任务中心重复，提交后缺少精确定位

**实测 V**：完成一次样例导出后出现全宽单列的全部4个任务，而根任务Tab原为双列。系统返回一次正常回到工作台，未观察到返回失效；问题是上下文重复和布局割裂。

**验收**：同一安装包样例显示25FPS；补24/25/30/60与23.976/29.97、未知值测试；视频参数默认值、媒体信息逐轨值和摘要一致；不能把真实高帧率简单误缩小100倍。

## 6. 横屏布局实施蓝图

以下是项目建议，不是照搬系统强制数值。以内容可用宽度 Wc 决策：窗口宽度减安全区、导航及页边距。

| 页面 | Wc 充足时 | 窄窗口/键盘可用空间不足时 |
| --- | --- | --- |
| 首页 | 一条主导入区 + 3列紧凑类型快捷项 | 主导入按钮换行，类型2列或1列 |
| 工作台 | 左预览约35–45%，右工具独立滚动 | 上预览下工具，一个主滚动 |
| 视觉配置 | 左效果预览，右参数约360–480vp，底部摘要/主操作 | 单栏，焦点自动可见 |
| 简单配置 | 最大约560–720vp表单，适量留白 | 自适应全宽 |
| 批量处理 | 左文件约280–360vp，右工具/配置 | 文件摘要可折叠，配置占主区域 |
| 任务中心 | 左任务列表，右当前任务详情；空间不足用单列表 | 任务列表→详情 |
| 媒体信息 | 分组导航+详情或两列信息卡 | 单列分组与展开 |

不要把“横屏利用空间”理解成所有输入框拉到全宽或所有页面双列。工作台/视觉配置需要同时观察不同对象；目标体积这种短表单保留呼吸空间反而更易读。

## 7. Agent 实施顺序与交付约束

1. **第一批：行为正确性**。UX-01～05及UX-21，补最小必要逻辑回归，不改整体视觉，先保证操作可信。
2. **第二批：状态和导航基础**。UX-06、14、17，确定单一任务中心、页面壳和草稿所有权；输出路由流转图。
3. **第三批：表单和宽屏核心流程**。UX-07、10、11、12，共用带标签字段和操作栏；先覆盖视频裁剪、图片缩放、批量合成三个代表流程。
4. **第四批：入口与结果整理**。UX-08、09、13、16，保留 actionId 兼容，合并视图入口，不删除底层能力。
5. **第五批：性能/可访问性/增强**。UX-15、18、19、20；播放与直接操控单独实现。

实施 agent 必须：

- 先读本文件和最新源码，核对已有修改，不能按过时行号盲改。
- 保留 HDS 原生导航/转场，查阅本机 API 24 声明后再调用新属性；不要为套布局引入新的 UI 库或全局迁移状态版本。
- 参数面板最终应只产出经校验 TaskParams；逐步把 `ActionConfigPanel` 的直接 enqueue 收敛到统一提交层，避免三个面板使用三种导航/防重规则。
- 提交层防重复点击并返回 taskIds；能力、预设、参数默认值共用一处定义，避免标题字符串 contains 驱动批量行为。
- 不覆盖原文件、不清空既有任务、不卸载应用来掩盖状态问题；测试素材与真实文件分开。
- 每批说明修改 ID、文件、测试结果、截图、未覆盖场景。纯 UI 变更不需要机械测试所有样式常量；关键行为测试必须执行生产逻辑而非复制实现。
- 不把历史验证文档里的“通过”当成当前修改的测试结果；尤其不能仅固定 ForEach key 后跳过实时进度验证。
